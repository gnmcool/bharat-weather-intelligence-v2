# D2 technical feasibility — direct Copernicus ERA5 (Option C)

**Status (30 Sep 2026):** feasibility note only.
- **The A/B/C decision is OPEN**, and D2 implementation is **not approved**.
- The D2 plan stays frozen at `f4d98b1` (`docs/M4.4-D2_PLAN.md`). This note does not modify it.
- This note documents **no retrieval, no credentials, no code, no release, and no change to `main`**.
- It checks whether the exact D2 extraction can be done through the Copernicus Climate Data Store (CDS). It also
  lists what a D2 plan revision would have to change if Option C were chosen.

Each item is marked:
- **Verified**: from current Copernicus/ECMWF documentation or an official API schema, with the source cited in §11;
- **Computed**: from `archive/points.json` (SHA-256 prefix `4919f87259fd`), with no network access;
- **Estimate**: arithmetic, not measured;
- **Unresolved**: not published, or conflicting.

## 2. Dataset, variable and product (verified)

| Item | Value |
| --- | --- |
| CDS dataset id | `reanalysis-era5-single-levels` ("ERA5 hourly data on single levels from 1940 to present") |
| Product type | `reanalysis` (not `ensemble_mean`, `ensemble_members` or `ensemble_spread`) |
| Variable | `total_precipitation` (GRIB short name `tp`) |
| Units | **metres** of water per hour step. mm = m × 1000 |
| Accumulation | reanalysis accumulations are "over the hour … ending at the validity date/time". The stamp `t` covers (t−1 h, t] |
| Grid | the CDS serves ERA5 **pre-interpolated to a regular 0.25° lat/lon grid**. The native model resolution is about 31 km (0.28125°). The "cell" is therefore an interpolated grid node, not a native model cell |
| Latency | updated daily, about 5 days behind real time (ERA5T) |
| Licence | CC-BY. The Copernicus licence allows use "for any purpose in so far as it is lawful", with the attribution text "Generated using / Contains modified Copernicus Climate Change Service information [Year]" |

**Consequence for D2 §5.4.** The plan's stamp rule applies unchanged: stamps 19:00Z (D−1) … 18:00Z (D) cover 23:30
IST (D−1) … 23:30 IST (D), with the same stated 30-minute offset. The plan's stamp convention was taken from the ECMWF
definition, and the CDS delivers that definition directly.

## 3. Request syntax (verified schema)

The inputs of the official process schema (`/api/retrieve/v1/processes/reanalysis-era5-single-levels`) are:
- `product_type`, `variable`, `year`, `month`, `day`, `time` (`"00:00"`…`"23:00"`);
- `data_format`: `grib` (default) or `netcdf`;
- `download_format`: `unarchived` (default) or `zip`;
- `area`: `[North, West, South, East]`.

**There is no `location` or `date` input.** `year`, `month`, `day` and `time` are lists, and the request covers every
combination of them.

The shape of a request for month M, shown for illustration only (no request has been sent):

```python
dataset = "reanalysis-era5-single-levels"
request = {
    "product_type": ["reanalysis"],
    "variable": ["total_precipitation"],
    "year": ["YYYY"],
    "month": ["MM"],
    "day": ["01", "02", ..., "<last day>"],
    "time": ["00:00", "01:00", ..., "23:00"],
    "data_format": "grib",
    "download_format": "unarchived",
    "area": [34.0, 72.25, 8.25, 94.75],   # computed bounding box of the 36 points, snapped outward to 0.25°
}
```

**The month boundary (computed from D2 §5.4).**
- IST day d₁ needs the stamps 19:00Z–23:00Z of the last UTC day of month M−1.
- Because the lists combine, one request with `month: [M−1, M]` would return **both full months**. In January it would
  also need two years.
- Two request shapes are therefore possible:
  - **(a) two requests per month:**
    - one for day `last(M−1)`, times `19:00`–`23:00`: 5 items;
    - one for the whole of month M, all 24 times: n × 24 items.
  - **(b) one request covering M−1 and M in full,** 59–62 days × 24 = 1,416–1,488 items, of which about 672–744 (the unused days of M−1) are
    discarded.
- Both shapes are small (§4). Choosing between them is part of a plan revision; this note does not decide it.

## 4. Points, extraction, format and volume

### 4.1 Nearest-node selection and the 30 km rule (computed)

| Quantity | Value |
| --- | --- |
| Distance from each point to its nearest 0.25° node (haversine, R = 6371.0 km) | 2.5 km (IN-35-640, South Andaman) … **16.5 km** (IN-07-delhi) |
| Points beyond 30 km | **none**. On a 0.25° grid the nearest node is never farther than about 19.7 km |
| Tie | **IN-11-243 (South Sikkim), longitude 88.375**, lies exactly midway between two nodes. A deterministic tie-break must be written into the plan, for example "the eastern node" |
| Land/sea | the CDS returns the nearest node **regardless of land or sea**. Open-Meteo chose a land cell with a 90 m DEM. Coastal and island points (e.g. South Andaman, Lakshadweep) may therefore use different nodes than the M4.4-B ERA5 values. This is to be recorded per point in the manifest and not "corrected" |

### 4.2 Can the 36 points be extracted without an India-wide grid?

- **Yes, technically** (verified schema): `area` can be set to a small box per point, for example ±0.25° around the
  nearest node. That means **36 separate requests per month** (72 with shape (a)), because a request takes one
  `area`.
- **One combined request** needs the box covering all 36 points: 8.25–34.0° N, 72.25–94.75° E, which is **104 × 91 =
  9,464 nodes** (computed).
- The item count does not depend on the area. One item is one variable × one level × one timestep (ECMWF definition,
  2019).

### 4.3 Volume and items per month (estimates)

The item counts below are computed; the byte sizes are estimates, assuming GRIB1 16-bit packing and about 0.2 KB of
header per message.

| Shape | Requests per month | Items per month | Downloaded |
| --- | --- | --- | --- |
| Combined box, shape (a) | 2 | 5 + n × 24 → **725–749** | about 9,464 × 2 B × 749 ≈ **14–15 MB** |
| Combined box, shape (b) | 1 | 1,416–1,488 | ≈ 27–28 MB |
| Per-point boxes (3 × 3 nodes), shape (a) | **72** | 36 × (725–749) | ≈ 36 × 749 × 0.2 KB ≈ 5–6 MB, but 72 queued jobs |

The published tables are the same as in D2 §12, about 0.3 MB per month. A plan revision would have to decide whether
the release keeps the raw GRIB file (≈ 15 MB) or a point-extracted derivative plus its checksum. Keeping the raw file
is the closer analogue of D2's `era5_response_*.json.gz`.

### 4.4 GRIB or NetCDF

| | GRIB | NetCDF |
| --- | --- | --- |
| `expver` | **documented** by ECMWF as a GRIB header key (`expver=0001` final, `0005` ERA5T) | appears as a variable-length string variable in the new converter's output (a user report, Oct 2024). Its exact layout is **not officially documented** |
| Request limits | the larger limit | **smaller than GRIB**: the NetCDF conversion adds processing (ECMWF announcement, 3 Apr 2025). The numbers are not published |
| Reading | needs ecCodes (a new dependency, e.g. `eccodes` / `cfgrib`) | needs netCDF4 / xarray |
| Fidelity | the native CDS product, with no conversion step | a converted product |

**Verified basis only:** GRIB is the format in which ECMWF documents `expver`. NetCDF's `expver` layout would have to be
confirmed on a first file.

## 5. ERA5T exclusion with `expver`

**Verified**
- ERA5T is marked `expver=0005`, and final ERA5 `expver=0001`, in the GRIB header.
- For the CDS, "ERA5T data for a month is overwritten with the final ERA5 data about two months after the month in
  question."
- ERA5T "could be different from the final release 2 to 3 months later" if serious flaws are found. ECMWF documented
  such differences for Sep–Dec 2021.

**Observed (a user forum report, Oct 2025; no ECMWF reply)**
- In a month still in ERA5T, the `total_precipitation` stamp at **00:00 UTC on day 1** was already `0001`, while the
  rest of that month was `0005`.
- This fits the hour-ending convention: the 00:00Z value belongs to the previous month.
- For D2, the stamps used for one IST month span **two** ECMWF release months: 19:00–24:00Z of the last day of M−1,
  and M itself.

**What `expver` can and cannot do**

| Question | Answer |
| --- | --- |
| Can D2 refuse any ERA5T value? | **Yes.** Check every one of the stamps used, for every point, for `expver == 0001`. Any `0005`, or a missing or unknown `expver`, refuses the month before publication. This is stronger than D2 §6's "final expected", which Open-Meteo could not verify |
| Does it guarantee the values never change upstream? | **No.** `0001` means "the final release as served now". ECMWF has published later corrections to final ERA5 (D2 §3 cites Jul–Nov 2024). D2's immutable release plus the §10.5 correction procedure still apply |
| Is the 70-day wait (R1) enough? | **Unresolved.** "About two months after the month" is not a fixed date. With the expver check, a request made too early is **refused** rather than publishing ERA5T. It still consumes an attempt |

## 6. The point-timeseries product (checked; not usable for D2)

**Verified (official process schema and dataset page, 30 Sep 2026)**
- `reanalysis-era5-single-levels-timeseries` **now lists `total_precipitation`**.
- It uses the nearest grid point; outputs are CSV or NetCDF; the licence is CC-BY 4.0.
- It is described as "a regridded subset of the full ERA5 data set", used by the ERA Explorer.

**Not established**
- Neither the dataset page nor the schema mentions `expver`.
- So **ERA5T cannot be excluded or detected** through this product, which fails requirement 7.
- It is not documented whether the product contains ERA5T or only final data.
- ECMWF's launch announcement described it as not recommended for operational systems.

**Conclusion:** per the owner's instruction, this product is **not used**.

## 7. Access, limits, queue and retries

### 7.1 Authentication (verified)
- A free ECMWF/CDS account and a **personal access token**.
- The configuration is `url: https://cds.climate.copernicus.eu/api` plus `key: <token>`. It can be supplied:
  - in `~/.cdsapirc` (cdsapi ≥ 0.7.7); or
  - via `ECMWF_DATASTORES_URL` / `ECMWF_DATASTORES_KEY`, or `~/.ecmwfdatastoresrc` (ecmwf-datastores-client, 0.5.3
    of 31 Jul 2026, Python ≥ 3.10).
- The dataset's Terms of Use must be accepted **manually on the dataset page**, once per account. The owner would do
  this; it cannot be done by the workflow.
- In D2 the token would be a GitHub Actions secret, never written to any manifest or log.
- **No credentials have been created.**

### 7.2 Request limits

| Item | Status |
| --- | --- |
| ERA5 hourly item limit | **not currently published as a number.** The last published figure is **120,000 items per request** (ECMWF, 2019, the old CDS). The 2025 announcement says NetCDF limits are now **smaller** than GRIB but gives no figures. An over-limit request fails with "403 … cost limits exceeded" / "Your request is too large" |
| D2's request against the limits | 5 to 1,488 items per request, about 1% of the last published GRIB figure. Well inside, but **not verifiable against a current published number** |
| Pre-check | the ecmwf-datastores-client has `apply_constraints` (valid combinations). The download form shows limit messages. A published cost-estimate call was **not found** |

### 7.3 Queue and concurrency
- **Unresolved.** No current per-user concurrency limit or queue time is published.
- Requests are queued jobs: submit, then poll, then download. Forum reports show queue delays from minutes to many
  hours.
- A GitHub Actions job is limited to 6 h. A plan revision would need a rule for a job still queued at timeout: record
  the `request_id`, and resume only by polling that id under a new committed request, never by resubmitting.

### 7.4 Safe retry behaviour

**Verified (client source)**
- `cdsapi` defaults are `retry_max=500` and `sleep_max=120`.
- It retries HTTP 408/429/500/502/503/504 and connection errors.
- It polls the job (`/tasks/{request_id}`) rather than resubmitting.
- For new-format tokens it delegates to `ecmwf.datastores`.
- The datastores client offers `submit()` (returns a `request_id`), `get_remote(request_id)`,
  `get_jobs(status=…)` and `download()`.

**Engineering inference (not an ECMWF statement)**
- A retried *submission* after a lost response could create a duplicate job.
- A CDS-safe pattern is therefore:
  - submit **once**;
  - write the `request_id` to the ledger immediately;
  - on network errors, **poll or download by `request_id`** instead of resubmitting;
  - before any resubmission, check `get_jobs` for an existing job with the same request;
  - use a small explicit retry cap instead of the default 500;
  - on 403 (cost limit or licence not accepted) or another 4xx, **stop, with no retry**.
- **Unresolved:** how long a completed result stays downloadable before it expires. This is not published in the
  pages checked.

## 8. Budget: keep the 200-call rule or replace it?

**Keep or replace (verified reasoning).** D2 §7's unit is Open-Meteo's **counted-call weight**, `locations ×
max(1, vars/10) × max(1, days/14)`. That formula has **no meaning on the CDS**, where there are no counted calls,
no location count and no per-call weight. The **number 200 cannot be retained as such.** If Option C is chosen, §7 has
to be replaced in a plan revision.

**What a CDS budget could count (estimates; for the owner to decide, not proposed as adopted)**

| Candidate unit | Normal month | Validation month (R2 repeat) |
| --- | --- | --- |
| Jobs submitted (combined box, shape (a)) | 2 | 4 |
| Items requested | 725–749 | 1,450–1,498 |
| Bytes downloaded | ≈ 15 MB | ≈ 30 MB |

**What carries over unchanged:**
- at most **two attempts per month**, where one attempt is the set of jobs for one month;
- the pre-check before every submission;
- the append-only ledger;
- refuse, never exceed.

**Unresolved:** whether a CDS-side limit exists that D2 should also mirror (§7.2, §7.3).

## 9. What a D2 plan revision would have to change if Option C were chosen

This is a list only; the plan is not modified by this note.

- **§3 (source):**
  - replace the Open-Meteo service with `reanalysis-era5-single-levels` / `total_precipitation` / `reanalysis`;
  - units in metres;
  - the Copernicus licence and attribution text.
- **§4 (request):**
  - the CDS request (§3 here);
  - the month-boundary shape, (a) or (b);
  - GRIB;
  - the area box.
- **§5.2 (grid cell):**
  - BWI's own nearest-node rule;
  - the tie-break (IN-11-243);
  - a per-point land/sea note.
  - §5.3–§5.6 stay unchanged, apart from the metre → mm conversion.
- **§6 (R1):** add the per-stamp `expver == 0001` check, and a refusal when it fails. The 70-day rule is kept or
  revised.
- **§7 (budget):** replace it (§8 here).
- **§8 (retry):** replace it with the CDS pattern in §7.4, plus the queue-timeout rule.
- **§10:**
  - the manifest records the dataset id, the request dict, the `request_id`, the `expver` per stamp, the GRIB SHA-256
    and the licence acceptance date;
  - raw GRIB retained or not (§4.3).
- **§11 (R2):** compare decoded values, not file bytes. Whether CDS returns byte-identical GRIB for identical requests is
  **unresolved**.
- **§12–§13:** new volume figures and tests (the expver refusal, the tie-break, metre conversion, the month-boundary
  stitching).
- **New dependencies:** `ecmwf-datastores-client` (or `cdsapi` ≥ 0.7.7) and ecCodes.
- **Owner tasks:** create the CDS account, accept the dataset licence, and store the token as a GitHub secret.

**Unchanged in every case:**
- ERA5's secondary, interim role;
- IMD primary; IMD and ERA5 never combined;
- the IST-day rule and 30-minute offset;
- the 30 km rule;
- E/G handling;
- no partial publication;
- immutable releases;
- the request-file trigger with no schedule;
- VM-1.1 and M4.4-D-SPEC-1.0.
