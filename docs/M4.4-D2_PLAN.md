## 1. Why D2 exists (prospective purpose)

D2 provides an **immutable, secondary rain reference for prospective M4.4-D verification** of CORE's issued items.
It has three uses and no others:

1. **Rain reference:** 24-h rain totals per **IST calendar day** at the 36 archive points.
2. **Horizon coverage:** every day that can fall in a prospective CORE issue's verification horizon **I+1 … I+6**
   (issues from 28 Sep 2026 onwards).
3. **Flood rain component:** the daily totals from which a later stage (D3) forms 72-h rain sums for the flood
   rain component, where applicable. D2 retrieves nothing extra for this.

**D2 must not:**
- modify CORE;
- modify V2 or `main`;
- alter the historical M4.2 releases or the M4.4-A/B/C results;
- introduce new verification metrics or change the M4.4-D methodology;
- fetch IMD data;
- retrieve any variable other than precipitation;
- become general weather-model verification;
- fetch ERA5 during planning.

---

## 2. ERA5's role and relation to IMD

- **ERA5 is the secondary / interim rain reference** for prospective M4.4-D verification. It is labelled
  "ERA5 reanalysis (secondary)" in every file, manifest and downstream result.
- **IMD remains the eventual primary rain reference.** It is used once IMD publishes its 2026 gridded rainfall, as
  a separate versioned supplement matched as CORE day D ↔ IMD file D+1 (M4.4-D-SPEC-1.0, decision Q2).
  **D2 does not replace IMD and does not fetch it.**
- **ERA5 and IMD are never combined.** There are separate releases, separate case tables, and separate counts,
  metrics and maturity states, and no merged or "best available" reference.
- **Different day definitions, never merged:**
  - ERA5 in D2 uses the **IST calendar day** (§5.4), the same day definition as CORE's issued rain.
  - IMD uses the **08:30–08:30 IST rain day** (file D = 24 h ending 08:30 IST on D).
  - D2 produces no 08:30-window ERA5 product.

## 3. Exact source

| Item | Value |
| --- | --- |
| Dataset | ECMWF **ERA5** reanalysis (not ERA5-Land, not a "seamless" mix, not ECMWF IFS analysis) |
| Service | **Open-Meteo Historical Weather API**, endpoint `https://archive-api.open-meteo.com/v1/archive`, with `models=era5` |
| Variable | `precipitation`, hourly, in mm. Open-Meteo defines it as the "sum of the preceding hour"; ECMWF defines hourly accumulations as "over the hour … ending at the validity date/time" |
| Temporal resolution | hourly |
| Spatial resolution | 0.25° grid (~25 km) |
| Availability | Open-Meteo updates ERA5 "daily with 5 days delay" |
| Preliminary vs final | ECMWF first issues **ERA5T** (preliminary) and overwrites it with **final ERA5 about two months after the month**. They can differ (ECMWF documents corrections for Sep–Dec 2021 and Jul–Nov 2024). Open-Meteo does not document when it switches, and does not expose ECMWF's version marker (`expver`). Hence the waiting period (§6) |
| Licence / terms | CC-BY 4.0 attribution. The free API is **non-commercial only**; the owner's confirmation that BWI's use is non-commercial is still **open** (§14). No paid key is used (B3 not approved) |

## 4. Exact request

One HTTP GET per retrieval (all 36 points in one request):

```
https://archive-api.open-meteo.com/v1/archive
  ?latitude=<36 latitudes, 4 decimals, comma-separated, in archive/points.json order>
  &longitude=<36 longitudes, same order>
  &hourly=precipitation
  &models=era5
  &timezone=GMT
  &precipitation_unit=mm
  &timeformat=iso8601
  &cell_selection=land
  &start_date=<first IST date of month − 1 day>   (UTC calendar date, YYYY-MM-DD)
  &end_date=<last IST date of month>              (UTC calendar date, YYYY-MM-DD)
```

- **Dates:** `start_date` begins one day earlier because IST day d₁ needs UTC hours from 19:00Z on d₁−1 (§5.4). A
  month of n IST days is requested as **n + 1 UTC days**.
- **Parameters:** `cell_selection=land` is Open-Meteo's documented default (a land grid cell chosen with a 90 m
  elevation model). It is written explicitly so the request is fully determined.
- **Headers:** the User-Agent identifies BWI V2 non-commercial research. No key and no secrets are sent.
- **Recorded:** the exact URL (with all parameters) and the response are recorded (§10).

## 5. Extraction

### 5.1 Points
The **36 fixed points** of `archive/points.json`, the same file as the prospective archive, with its SHA-256
recorded in the manifest. The response must contain exactly 36 locations, in request order; otherwise the retrieval
is refused.

### 5.2 Grid cell
For each point, the response's `latitude` / `longitude` are the ERA5 grid cell Open-Meteo used. The manifest
records, per point:
- the requested coordinates;
- the returned cell coordinates;
- the **distance** (haversine, km, using an Earth radius of 6371.0 km);
- the returned elevation, as information only; nothing is elevation-adjusted.

### 5.3 30 km eligibility
A point is eligible only if its cell distance is **≤ 30 km** (VM §6 rule 4). An ineligible point keeps its hourly
values in the hourly table, but **every one of its IST-day values is null with reason G** ("ERA5 cell > 30 km").

### 5.4 IST-day aggregation and the UTC → IST boundary

| Item | Rule |
| --- | --- |
| IST calendar day D | 00:00–24:00 IST = 18:30Z (D−1) … 18:30Z (D) |
| ERA5 hours | stamped at full UTC hours; each value is the sum over the preceding hour (t−1 h, t] |
| Stamps used for day D | the **24 stamps 19:00Z (D−1), 20:00Z, …, 18:00Z (D)** |
| Interval actually covered | 18:00Z (D−1) … 18:00Z (D) = **23:30 IST (D−1) … 23:30 IST (D)** |
| Known offset (limitation) | the ERA5 day starts and ends **30 minutes earlier** than the IST calendar day. Hourly data cannot be split at :30. Each result using D2 states the offset. It is the same convention as the M4.4-B ERA5 rain day |
| Not known | how Open-Meteo builds CORE's own daily rain for Asia/Kolkata (+5:30); D2 does not assume it matches |
| Daily value | the sum of the 24 hourly values, in mm, computed in float64 and stored as float32 |

### 5.5 Completeness requirement
A day has a value **only if all 24 stamps exist in the response time axis and all 24 values are non-null**. A day
with fewer than 24 non-null values is null, and records `hours_present` (0–24).

### 5.6 Missing-data handling

| Case | Treatment |
| --- | --- |
| Source hour null in a valid response | day null, reason **E** ("ERA5 hours missing: n of 24"); never zero, never interpolated, never filled from another source or model |
| Cell > 30 km | day null, reason **G** |
| Request failed, malformed or structurally incomplete (wrong location count, missing timestamps) | **the month is refused** (reason **D**); nothing published (§8) |

- E-reasons are published: they describe a valid source gap, not a failed retrieval. Every E-day is listed in the
  gap report, and any E-day is reported to the owner in the run summary.
- Downstream, a null day is never a negative event (M4.4-D-SPEC-1.0 §16).
- **Owner clarification (30 Sep 2026).** A monthly release is published when the monthly response is structurally
  valid. Days with incomplete hourly coverage are marked `E` with the specific missing-data reason (hours present,
  n of 24). These E-days are:
  - excluded from M4.4-D verification metrics;
  - never converted to zero;
  - never treated as forecast misses.

  The missing-day information stays in the manifest (gap report, listed with its SHA-256) and in the archive-index
  record (§10.4). The verification sample can therefore always tell source missingness from forecast failure.

## 6. Final-data waiting period (decision R1)

- Month M is retrieved **no earlier than 70 days after its last day**, when final ERA5 is expected. A request made
  earlier is refused before any HTTP call.
- **Preliminary ERA5T is never published.**
- **A published ERA5 release is never mutated or replaced.** The objective is one stable, reproducible reference
  dataset per month. The only exception is a documented correction (§10.5), which adds a new version and never
  alters the old one.
- Because Open-Meteo cannot show the ERA5 version, each manifest states "retrieved N days after month end; final
  ERA5 expected; ERA5T/final not distinguishable through Open-Meteo".

**Earliest retrieval dates.** These are a consequence of R1, not a readiness projection:

| 2027-01 | 31 | 11 Apr 2027 |

At the earliest M4.4-D review point (27 Dec 2026), only September 2026 can have an ERA5 reference release.

## 7. Call budget

- **Definition of a counted call.** For every HTTP request **sent** to the ERA5 endpoint, whatever its response
  (success, error, rate-limit reply, malformed body), including retries and the controlled repeat of R2:
  `weight = locations × max(1, variables / 10) × max(1, UTC days / 14)`, **rounded up** to a whole number.
  - This is Open-Meteo's counting rule for multi-location and multi-day requests, applied conservatively: a refused
    or failed request is counted as if it succeeded.
  - Requests to other hosts (e.g. GitHub) are not Open-Meteo calls.
- **Per request:** 36 × 1 × (n + 1)/14:
  - 31-day month → 36 × 32/14 = 82.29 → **83**;
  - 30-day month → 79.71 → **80**;
  - 28-day February → 74.57 → **75**.
- **Budget:** at most **200 counted calls per calendar month (UTC)** for all D2 requests together.
- **Enforcement (refuse, never exceed):**
  1. An append-only ledger on archive-index (§10.4) records each request's weight at the moment it is sent.
  2. **Before every request**, the job computes `spent this month + weight of the next request`. If that exceeds
     200, it **does not send** the request and records a refusal ("budget").
  3. Consequently a normal month allows at most two attempts (83 + 83 = 166; a third would reach 249).
- **Also stops immediately:** the free-tier limits (< 10,000 per day, 5,000 per hour, 600 per minute) are far
  above D2's use. A reply saying the daily or monthly quota is exhausted stops the run immediately, with no retry.

## 8. Retry, backoff and failure handling

| Situation | Behaviour |
| --- | --- |
| Network error, HTTP 5xx, malformed or truncated JSON | retry, with waits of 5 s then 10 s between attempts, **only while the budget pre-check (§7) passes**. The attempt cap is therefore 2 per month (1 in the R2 validation month, where the repeat uses the second slot) |
| HTTP 429 (per-minute limit) | wait 65 s, then retry under the same budget rule |
| Quota-exhausted reply (daily/monthly) | stop at once; no retry |
| HTTP 4xx other than 429 | stop; no retry (a request error) |
| All permitted attempts fail, the budget is reached, or validation fails | **the month is refused.** A refusal record (§10.4) stores the reason, the attempts, the counted calls, the error texts (without secrets) and the code commit. **No release, draft or partial file is published.** A new committed request is needed to try again |

- **Nothing partial is ever published.** Only a month that passes every validation check (§13 B) receives an
  immutable release.
- A draft left by an interrupted publication is deleted before the refusal is recorded. A published release is
  never deleted.

---

## 9. Trigger (no schedule)

- A month is retrieved **only** through an explicit committed request: a file
  `reference/era5_request.json` on the review branch `m4-history`, containing
  `{"months": ["YYYY-MM"], "purpose": "…", "repeat_check": false}`.
- Committing a change to that file starts one GitHub Actions run of the D2 workflow for exactly the listed months.
- **There is no cron schedule.** No run starts without a new commit to the request file.
- The workflow runs on `m4-history` and never on `main`. It never touches the daily archive or its workflow.

## 10. Versions, provenance and releases

### 10.1 Release naming
- One immutable GitHub release per month: **`ref-era5-YYYY-MM`**.
- A correction is `ref-era5-YYYY-MM-v2` (then `-v3` …), per §10.5.

### 10.2 Release files

| File | Content |
| --- | --- |
| `era5_hourly_YYYY-MM.parquet` | point_id, utc_time, precipitation_mm (nullable), cell_lat, cell_lon |
| `era5_ist_day_YYYY-MM.parquet` | point_id, ist_date, precip_ist_day_mm (nullable), hours_present, reason (null / E / G), cell_distance_km, eligible |
| `era5_response_YYYY-MM.json.gz` | the exact API response body (gzip without a timestamp, so the file is deterministic) |
| `gap_report_ref-era5-YYYY-MM.json` | expected versus present hours per point, and every E- and G-day |
| `manifest_ref-era5-YYYY-MM.json` | §10.3 |

### 10.3 Manifest contents
- **Dataset:** `dataset: "era5_reference_supplement"`, `role: "secondary rain reference (interim)"`, `month`,
  `schema_version`.
- **Source:** endpoint, the exact request URL (all parameters), `models=era5`, the licence note.
- **Version:** "final ERA5 expected; retrieved N days after month end (≥ 70); ERA5T/final not distinguishable
  through Open-Meteo".
- **Retrieval:** the UTC timestamp of each request sent, the HTTP status, and the counted weight per request.
- **Coverage:** the IST dates covered (d₁ … dₙ) and the UTC request range (d₁−1 … dₙ).
- **Code:** the code commit (git SHA), the workflow run URL, and the request-file commit.
- **Points:** `archive/points.json` SHA-256, plus per point the requested and cell coordinates, distance,
  elevation and eligible flag.
- **Aggregation:** the rule text (§5.4), including the 30-minute offset statement.
- **Files:** for every file, its name, bytes, rows and **SHA-256**.
- **Repeat check:** `repeat_check`, and its result reference if one was performed (§11).

### 10.4 Checksums and archive-index record
- Before publication, every file is hashed and checked against the manifest. After publication, every asset is
  downloaded again and checked, and the attempt to add, overwrite or delete an asset must be rejected (immutability
  verified).
- Append-only archive-index records:
  - `reference/era5/index/YYYY-MM.json`: manifest SHA-256, release URL, checksum and immutability check results,
    the list of E- and G-days (point, IST date, reason, hours present),
    run id;
  - `reference/era5/refused/YYYY-MM_<run>.json` for every refusal;
  - `reference/era5/budget/<UTC-YYYY-MM>.jsonl`: the call ledger, one line per request sent.
- Existing records are never overwritten.

### 10.5 Correction procedure
- A published month is corrected **only** for a documented defect: an extraction bug, or a documented upstream
  ERA5 correction. The owner must approve it, and a committed request marks it as a correction.
- The correction is a new release `ref-era5-YYYY-MM-v2`. Its manifest carries `supersedes`, the reason, and a
  value-level comparison with the previous version.
- The old release stays immutable and remains the reference for any result that used it. Every downstream result
  names the exact release it used.

## 11. Reproducibility check (decision R2)

- **Routine retrievals are single-pass**, validated by checksum, completeness and manifest checks. There are no
  routine duplicate retrievals.
- **One controlled repeat, during D2 validation only:** for one selected month (the first month retrieved), a
  second identical request is sent within the same run, inside the budget (80 + 80 = 160 for a 30-day month).
- **Compared:**
  - every hourly value (exact equality, nulls included);
  - every IST-day value and the monthly totals per point;
  - the SHA-256 of the canonical hourly and daily tables;
  - completeness (hours present and E/G reasons).
  - The JSON bodies are **not** compared byte for byte, because they contain a server timing field
    (`generationtime_ms`) that changes on every call.
- **Recording:** the result is stored as validation evidence on archive-index
  (`reference/era5/validation/YYYY-MM_repeat.json`) and referenced in that month's manifest.
- **If the two retrievals differ:** the month is **not** published, and the difference is reported to the owner.

## 13. Acceptance criteria

### A. For this design plan (before D2 implementation may be approved)
1. The owner has decided R1 (final ERA5, retrieved at least 70 days after month end, no ERA5T) and R2 (one
   controlled repeat during validation only). **Done: recorded in §6 and §11.**
2. The owner has accepted the budget (≤ 200 counted calls per calendar month, refuse rather than exceed) and the
   committed request-file trigger with no schedule. **Done: §7 and §9.**
3. The owner confirms that BWI's use of the free Open-Meteo API is non-commercial. **Open.**
4. The owner accepts the release naming, file set, manifest fields, archive-index records and correction procedure
   (§10).
5. The owner accepts the IST-day aggregation, including the stated 30-minute offset (§5.4), and the E/G missing-data
   treatment (§5.6).

### B. For a later D2 implementation (after approval)
1. **Source/request reproducibility:** the request URL is built exactly as in §4 (unit-tested against a fixed
   expected string), and the manifest records it.
2. **Complete monthly coverage:** every IST day of the month and all 36 points are present in the day table (a
   value, or a null with E/G). A structurally incomplete response is refused.
3. **Correct 36-point extraction:** 36 locations in `points.json` order; the manifest records the file SHA-256; a
   response with a different location count or order is refused.
4. **30 km eligibility:** the distance is computed as in §5.2; a known-answer test with a cell over 30 km gives G for
   every day; exactly 30.0 km is eligible.
5. **Correct IST-day aggregation:** known-answer tests for the 19:00Z (D−1) … 18:00Z (D) window, including the month
   boundary (d₁ uses the d₁−1 UTC hours) and 23 hours → null with E, never zero.
6. **No partial publication:** fault-injection tests (network failure, malformed body, quota reply, validation
   failure, interrupted publication) leave no release and no draft, and do leave a refusal record.
7. **Manifest/hash verification:** every file's SHA-256 matches the manifest before and after publication; a
   tampered file is refused.
8. **Immutable release verification:** after publication, attempts to add, overwrite and delete an asset are
   rejected, and GitHub's immutable flag is true.
9. **Archive-index provenance:** the index, refusal, budget-ledger and validation records exist and are
   append-only, with no record overwritten.
10. **Controlled repeat-retrieval comparison (R2):** it is performed once in validation, compares values, totals,
    table checksums and completeness (§11), and its evidence is recorded.
11. **Budget enforcement:** a test shows a request is **not sent** when `spent + weight > 200`; the ledger reconciles
    with the manifest weights; the first real month's measured counted calls are reported.
12. **Final-data waiting period:** a request for a month less than 70 days after its end is refused before any HTTP
    call.
13. **Regression — nothing else changed:**
    - CORE still at `2840f8d` (`core-v1.0`);
    - `main` / V2 unchanged by D2;
    - all existing releases (history-*, archive-daily-*, legacy) still immutable with unchanged checksums;
    - the recorded M4.4-A/B/C and census result hashes unchanged;
    - offline suites (archive, history, verification, api-v2) and CI pass.
