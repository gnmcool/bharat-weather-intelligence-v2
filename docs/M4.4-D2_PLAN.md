# M4.4-D D2 — ERA5 reference layer: design and resource plan (not approved; nothing implemented)

**Status:** plan only (30 Sep 2026). No ERA5 has been fetched, no reference supplement created, the archive is not
modified and no scheduled job is added. D2 starts only on the owner's approval. It implements §6 and §22 (D2) of
M4.4-D-SPEC-1.0 (`docs/M4.4-D_PROSPECTIVE_VERIFICATION.md`).

## 6. Purpose (kept minimal)

D2 provides **one thing**: an immutable ERA5 reference layer of **24-h rain totals per IST calendar day at the 36
archive points**, covering every day that can fall in a prospective CORE issue's horizon **I+1 … I+6** from
28 Sep 2026. Flood's 72-h rain comes from three consecutive daily values at a later stage (D3); it needs no extra
retrieval.

D2 is not:
- matching or eligibility (D3), event matching (D4) or scoring;
- any historical verification infrastructure;
- any other variable (heat and cold are not verifiable: no temperature or gust is retrieved);
- an 08:30-window ERA5 product (CORE's day is the IST calendar day; IMD is handled separately, §7).

## 1. Exact ERA5 source

| Item | Value | Basis |
| --- | --- | --- |
| Dataset / product | ECMWF **ERA5** reanalysis, served by the **Open-Meteo Historical Weather API** with `models=era5` (ERA5 only; not ERA5-Land, not "seamless", not ECMWF IFS) | Open-Meteo documentation; the same request the historical backfill used (`history/sources.py::era5`) |
| Variable | `precipitation` (hourly) only | the only variable any verifiable M4.4-D risk needs (rain, flood rain component) |
| Hourly value definition | sum of the preceding hour (Open-Meteo: "sum of the preceding hour"; ECMWF: "accumulations are over the hour … ending at the validity date/time") | documentation |
| Temporal resolution | hourly | Open-Meteo: ERA5 hourly |
| Spatial resolution | 0.25° (~25 km) | Open-Meteo documentation |
| Interface | `GET https://archive-api.open-meteo.com/v1/archive` with `latitude=…,longitude=…` (36 comma-separated), `hourly=precipitation`, `models=era5`, `timezone=GMT`, `start_date`, `end_date`; default grid-cell selection (land cell by Open-Meteo's 90 m elevation model), identical to the historical backfill | `history/sources.py` |
| Licence / terms | CC-BY 4.0 attribution; the free API is **for non-commercial use only** | Open-Meteo terms. **The owner must confirm that BWI's use is non-commercial**; otherwise a paid plan is required, which is not approved (B3) |
| Availability lag | "daily with 5 days delay" | Open-Meteo documentation |
| Preliminary vs final | ECMWF publishes **ERA5T** (preliminary, about 5 days behind real time) and overwrites it with **final ERA5 about two months after the month**. The two can differ: ECMWF documents corrected flaws for Sep–Dec 2021 and Jul–Nov 2024. **Open-Meteo does not document whether, or when, it replaces ERA5T with final ERA5, and does not expose ECMWF's version marker (`expver`)** | ECMWF ERA5 documentation; Open-Meteo documentation (silent) |

**Versioning decision needed (R1).** Because the version served cannot be seen, the plan proposes:

- **Recommended: final-only retrieval.** Each calendar month is retrieved once, no earlier than **70 days after the
  month ends** (two months plus margin), and labelled "expected final ERA5 (ERA5T/final not distinguishable
  through Open-Meteo)".
  - This delays reference availability by about 2.5 months.
  - It does not limit M4.4-D: scoring cannot begin before 27 Dec 2026 in any case, and floors take longer.
- **Alternative: an interim ERA5T supplement plus a later final version.** The ERA5T supplement would be
  retrieved at 7 days or more after month end and labelled "preliminary". A final version would follow at 70 days
  or more, recorded as a new versioned supplement with a value-level comparison against the first.
  - This means twice the retrievals and two reference versions to track.

## 2. Exact extraction

| Step | Rule |
| --- | --- |
| Points | the 36 fixed points of `archive/points.json` (same file, same SHA-256 as the prospective archive; recorded) |
| Spatial matching | Open-Meteo's grid cell for each point, recorded per point: returned latitude/longitude, distance to the point (haversine km) and cell elevation. **Eligible only if the distance is ≤ 30 km** (VM §6 rule 4); otherwise every day of that point is reason **G**. The historical backfill measured a maximum of 20.4 km for these 36 points |
| Temporal aggregation | IST day D = the sum of the 24 hourly values stamped 19:00Z (D−1) … 18:00Z (D). This is exactly the existing `ist_day` aggregation (`history/common.py::aggregate_daily`) used for M4.4-B's ERA5 rain |
| IST-day limitation | because hourly values are preceding-hour sums, this day covers 18:00Z (D−1) … 18:00Z (D) = 23:30 IST (D−1) … 23:30 IST (D): **30 min earlier than the IST calendar day**. This is a named limitation, as in M4.4-B. How Open-Meteo builds CORE's own daily sum for Asia/Kolkata (a +5:30 offset) is not documented |
| Request range | month M's IST days d₁ … dₙ need UTC dates d₁−1 … dₙ, so one request covers n + 1 UTC days |
| Coverage | calendar months from **September 2026** onwards. September is needed for the first horizons (issue 28 Sep → days 29–30 Sep) and for the 72-h sums, which reach back two days |
| Missing data | a day has a value **only if all 24 hours are present**; otherwise the value is null, with reason **E** (source hours missing: n of 24) or **G** (cell > 30 km). Never zero, never interpolated, never filled from another source. Hours present and missing are stored per point-day |
| Stored tables | (a) `era5_hourly_<M>.parquet`: point, UTC hour, precipitation, cell lat/lon; (b) `era5_ist_day_<M>.parquet`: point, IST date, 24-h sum or null, hours present, reason, cell distance; (c) the raw API response, gzip, for audit; (d) the manifest |

## 4. Quota and rate limits

| Item | Value |
| --- | --- |
| Documented limits (free, non-commercial) | < 10,000 calls/day, 5,000/hour, 600/minute (Open-Meteo terms) |
| Counting (as already used by the archive, `om_weight`) | each location counts; > 10 variables or > 14 days count proportionally more |
| One monthly request | 36 locations × 1 variable × (32 UTC days / 14) ≈ **82 counted calls** (a 30-day month ≈ 80) |
| Expected rate | ≈ 82 counted calls per month (≈ 165 with R2). The daily archive already uses ≈ 108 calls/day from separate runs |
| Maximum reasonable budget | **≤ 200 counted calls per month for D2**, and no single run above 200 (≈ 2 % of one day's free limit). Anything above that stops the run |
| Retry / backoff | the existing bounded client (`history/sources.py`): at most 4 attempts per request; backoff 5 s × 2ⁿ (≤ 60 s); on HTTP 429, wait 65 s. A malformed body is retried within the same 4 attempts. A reply reporting the daily or monthly quota spent stops the run immediately (`QuotaExhausted`), with no further attempts |
| Failure handling | a month whose request fails after the bounded attempts is **refused** (reason D) and recorded on archive-index with the error. **Nothing partial is published.** The month is retried only in the next owner-approved run; there are no automatic retries across days |
| Where it runs | a GitHub Actions job triggered by a committed request file (the pattern the historical backfill used: auditable, no cron). **No scheduled job.** A monthly schedule would need a separate owner decision. The workspace itself cannot reach Open-Meteo (it returned HTTP 429 on 30 Sep) |
| Not relied on | runner IP differences to get around any limit |

## 5. Versioning and provenance (per reference supplement)

- **Release:** `ref-era5-YYYY-MM` (immutable GitHub release, as for `history-*`). A correction becomes a new release
  `ref-era5-YYYY-MM-v2` with a documented reason. **Nothing is overwritten.**
- **Manifest (`manifest_ref-era5-YYYY-MM.json`):**
  - **Source:** `archive-api.open-meteo.com/v1/archive`, the exact request parameters (no secrets), dataset "ERA5
    (ECMWF) via Open-Meteo, `models=era5`".
  - **Dataset version:** "expected final ERA5 — retrieved N days after month end" (R1), plus the statement "ERA5T
    and final ERA5 are not distinguishable through Open-Meteo".
  - **Retrieval:** UTC timestamp of each request, HTTP statistics, counted calls.
  - **Covered dates:** the IST dates covered and the UTC request range.
  - **Code:** code commit, and `archive/points.json` SHA-256.
  - **Per point:** returned cell latitude/longitude, distance and elevation.
  - **Files:** name, bytes, rows and SHA-256 of every file.
  - **Gap report:** expected versus present hours, and point-days with reasons E and G.
- **archive-index:** an append-only record `reference/era5/index/YYYY-MM.json` with the manifest SHA-256, release URL,
  checksum checks and immutability checks (add/overwrite/delete attempts rejected), exactly as for the daily
  archive.
- **Downstream use (D3 onwards):** every M4.4-D result records the supplement tags and manifest SHA-256 values used
  (§19 of the specification).

## 7. Relation to IMD

- **ERA5 is the interim, secondary rain reference.** It is labelled "reanalysis, secondary" in every supplement and
  every downstream result.
- **IMD is the primary rain reference once 2026 is published.** It becomes a separate, versioned supplement (e.g.
  `history-imd-raw-2026`, VM §15), matched with **CORE day D ↔ IMD file D+1**, with the approximately 8.5 h offset
  documented (decision Q2). That is **not part of D2**, and nothing is retrieved for IMD now.
- **IMD and ERA5 are never combined:**
  - separate supplements;
  - separate case tables;
  - separate counts, metrics and maturity states;
  - no merged or "best available" reference.

## 8. Acceptance criteria

**Before D2 may be approved (plan level):**
1. The owner decides R1 (final-only, or interim plus final) and R2 (value-level repeat check: yes or no).
2. The owner confirms BWI's use of the free Open-Meteo API is non-commercial, or decides otherwise.
3. The budget is accepted (≤ 200 counted calls per month for D2).
4. The trigger is accepted: a request-file-triggered GitHub Actions run, no cron.
5. The release naming, manifest fields and archive-index record format (§5) are accepted.

**Before a D2 implementation can be accepted (after approval):**
1. Offline known-answer tests pass before any retrieval:
   - IST-day construction (19:00Z … 18:00Z, 24/24 hours);
   - a missing hour gives a null day with reason E, never zero;
   - a cell over 30 km gives G;
   - a month boundary (the request covers d₁−1);
   - refusal on a malformed or failed response;
   - the quota-stop path;
   - manifest checksums; tampered-file refusal;
   - the published supplement is immutable (add/overwrite/delete rejected).
2. A dry run on a synthetic source, with no network, produces the full release layout.
3. The first real retrieval (one month, within budget) is published, verified and indexed. Its measured size and
   counted calls are reported against §3 and §4.
4. No existing release, census or result hash changes. CORE stays at `2840f8d`. `main`'s daily capture is
   untouched by D2.
5. Offline regression suites pass (archive, history, verification, api-v2) and CI is green.
