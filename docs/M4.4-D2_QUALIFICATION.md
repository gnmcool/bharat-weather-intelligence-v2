## 1. Why January 2025
- **Final ERA5:** the manual download of 30 Sep 2026 showed `expver=0001` on all 749 hours.
- **Hardest request case:** the boundary request falls in the previous year (31 Dec 2024), and the month has 31 days
  (744 hours).
- **Comparison point:** the manual files are test evidence only. They are never uploaded, published or substituted
  for a CDS retrieval. Their SHA-256 values are month `75d3e151…` and boundary `b499ee50…`.
- **Limitation:** January is dry over most of India, so rainfall magnitudes are small.

## 2. What is retrieved
These are exactly the production D2 requests, built by `era5_common.build_requests("2025-01")`:

| Request | Content | Items |
| --- | --- | --- |
| Boundary | 31 Dec 2024, 19:00–23:00 UTC | 5 |
| Month | January 2025, days 01–31, 00:00–23:00 UTC | 744 |

Both use `reanalysis-era5-single-levels`, `reanalysis`, `total_precipitation`, GRIB, unarchived, area
`[34.0, 72.25, 8.25, 94.75]`.

## 3. Sequence
The production functions are used unchanged:
1. `era5_run.preflight`: authentication plus the partial licence check. No job is created.
2. `era5_run.run_retrieval(1)`: R1, two CDS jobs. Submit once, request-id ledger, poll, download, GRIB structure,
   `expver=0001`, 36-point extraction, IST-day aggregation.
3. `era5_run.run_retrieval(2)`: R2, two CDS jobs, identical requests.
4. `era5_r2.compare`: the value-level criterion of plan §11.
5. `era5_run.build_stage`: the release package is built, labelled, and **not published**.

**At most four CDS jobs.** The production four-job guard applies. There is no automatic third retrieval, and a refused
or failed qualification submits nothing more.

## 4. Separation from the official D2 path (enforced in code and tests)
- **Months:** an allow-list containing only `2025-01`. Every other month, including `2026-09`, is refused before any
  CDS call.
- **Records:** the ledger, result and refusal records are written only under `qualification/era5/…` in a worktree of
  the separate branch **`era5-qualification`**. The driver refuses any other branch (`archive-index`, `main`,
  `m4-history` or any other) and any index containing `reference/era5/`.
- **No publication:** no GitHub release client is passed (the driver refuses one), and the module does not reference
  any production publication or index function. The test suite checks this structurally.
- **Outputs:** written to a local work directory `QUALIFICATION_era5_2025-01/` with `QUALIFICATION_README.txt`. The
  manifest carries `"QUALIFICATION_NOTICE"` and `"official": false`. They are uploaded as a GitHub Actions artifact
  named `QUALIFICATION-not-a-D2-reference-era5-run-<id>`, kept for 90 days.
- **Request files:** the official `reference/era5_request.json` is never read or written. The official D2 workflow is
  not triggered.
- **September 2026:** its ledger, retrieval slots, release and index are untouched.

## 5. Trigger
- Committing `reference/era5_qualification_request.json` on `m4-history`, containing
  `{"month": "2025-01", "purpose": "…"}`, starts one run of `era5-qualification.yml`. There is no schedule and no
  manual trigger.
- `CDS_API_KEY` is exposed only to the qualification step and is never recorded.

## 6. What it does not show
- Behaviour on preliminary ERA5T data; this remains covered by offline tests.
- Queue times in December.
- That 2026-09 will be final on 9 Dec 2026.
