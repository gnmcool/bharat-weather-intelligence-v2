# M4.4-D — prospective verification of CORE's issued risk outputs (specification)

**Version: M4.4-D-SPEC-1.0 — FROZEN.** Approved by the owner on 30 Sep 2026, with the decisions in §23. Any
change requires a new version number. It applies VM-1.0 as amended by VM-1.1 (`docs/VERIFICATION_METHODOLOGY.md`).

**Stages:** implementation goes stage by stage (§22), each on the owner's approval. D1 is approved; D2–D7 are
not started. Scoring has not begun.

**Scope.** M4.4-D verifies **what CORE actually issued**. The chain is:

> forecast → CORE risk engine → issued CORE risk level → subsequent reference observation →
> hit / miss / false alarm / correct negative

It is **not**:
- raw model verification (M4.4-A/B);
- model agreement (M4.4-C);
- historical rule replay (C2);
- an impact forecast or a damage/loss assessment.

**Facts this specification relies on (checked 30 Sep 2026).**
- CORE is frozen at `core-v1.0` (`2840f8d`). Its rules are in `backend/app/engines/risk.py` and `thresholds.py`.
- The prospective archive's CORE capture is `archive/collect.py → core_snapshot()`, with schemas
  `CORE_RISK_SCHEMA` and `CORE_DAILY_SCHEMA` in `archive/common.py`.
- Published prospective releases: `archive-daily-2026-09-28` and `archive-daily-2026-09-29` (immutable). On
  28 Sep, three collection attempts were refused before the day was published.

## 0. Corrections to the brief (to be confirmed by the owner)

1. **CORE has no verification logic, and its ±1-day rule is not a verification rule.** The ±1 day in CORE is part
   of CORE's model-agreement label: `risk.py::_confidence` counts a model as agreeing if its level is at least the
   issued level minus one within ±1 day of the best-match peak. M4.4-D therefore needs a **verification timing
   tolerance of its own**. §4 sets ±1 day (owner decision Q1). This tolerance is the M4.4-D verification
   methodology; it is **not** an existing CORE verification rule.
2. **CORE's issued risk is not a blended ECMWF/GFS/ICON forecast.** CORE derives its issued level from Open-Meteo's
   "best-match" forecast. Best-match's model composition over India is not documented in the available evidence
   (Q6), and it is not inferred from the M4.4-A/B/C model work. ECMWF, GFS and ICON feed only CORE's agreement
   label, which is contextual provenance, not the forecast being verified.
   - M4.4-C = independent ECMWF/GFS/ICON model agreement.
   - M4.4-D = CORE's actual issued risk output.
3. **CORE's rain day is the IST calendar day** (00:00–24:00 IST, `settings.timezone = Asia/Kolkata`). **IMD's
   day is not:** an IMD file dated D holds the 24 h ending 08:30 IST on D (measured, `docs/HISTORY.md`). The
   mismatch is handled explicitly in §6 (decision Q2: CORE day D ↔ IMD file D+1, an approximately 8.5 h offset
   named as a reference limitation).

## 1. Objective

For each verifiable CORE risk (§7), and separately for each level threshold ℓ ∈ {Watch = 1, Alert = 2,
Severe = 3}, count **hits, misses, false alarms and correct negatives** of CORE's issued items against a named
reference. From those counts, compute POD, FAR, CSI and frequency bias (§10). Results are always risk-specific,
level-specific and reference-specific. There is no overall CORE score and no score across hazards.

## 4. Event matching and the timing tolerance (approved: decisions Q1, Q3)

**Issue date.** `I` = the IST calendar date of `core_generated_at_utc`. CORE's day I+0 is already partly elapsed
at issue, by a varying amount: the two published snapshots were taken at 01:41 IST (28 Sep) and 16:59 IST
(29 Sep), because GitHub starts scheduled runs late and the first day was a manual run.

**Evaluation horizon `H(I)`** = the IST days that are verified for an issue: **days I+1 … I+6** (decision Q3).
- Day I+0 is excluded because it is partly elapsed at issue. An issued period entirely on day I+0 is recorded but
  not verified (reason: "elapsed at issue").
- The exact issue timestamp is kept for every record, because snapshots occur at materially different times of
  day.

**Unit of verification (one case)** = (point p, risk r, issue date I, level threshold ℓ). One issue produces at
most one issued item per risk and point, so there is **at most one forecast event per case**.

**Forecast event** at ≥ ℓ: the issued level L ≥ ℓ. Its forecast event days are `F = days(period_start …
period_end) ∩ H(I)`.
- CORE's period spans the first to the last day with level > 0 at any level. It is not restricted to days at ≥ ℓ,
  and CORE does not issue per-day levels. The whole period therefore counts as the claimed window. It is **not**
  narrowed to the peak day.

**Matching window with the tolerance** (decision Q1: ±1 day around the issued CORE period):
`W = days(min(F) − 1 … max(F) + 1) ∩ H(I)`.
- If CORE issues an event for day D, the verification window is D−1 to D+1, subject to the horizon.
- The tolerance is applied once, to the issued period. It never widens the horizon.
- This tolerance is the M4.4-D verification methodology, **not** an existing CORE verification rule.

**Reference event day:** a day d in the reference whose value meets CORE's own criterion for ≥ ℓ on that day
(for rain: 24-h total ≥ the level threshold).

**Outcome of one case:**

| Issued | Reference | Outcome |
| --- | --- | --- |
| L ≥ ℓ | ≥ 1 available day in W with a reference event ≥ ℓ | **hit** |
| L ≥ ℓ | every day of W available, none ≥ ℓ | **false alarm** |
| L ≥ ℓ | no event among available days, ≥ 1 day of W unavailable | **excluded: reference incomplete** |
| L < ℓ | ≥ 1 available day in H(I) with a reference event ≥ ℓ | **miss** |
| L < ℓ | every day of H(I) available, none ≥ ℓ | **correct negative** |
| L < ℓ | no event among available days, ≥ 1 day of H(I) unavailable | **excluded: reference incomplete** |

**Multiplicity and double counting**
- **One forecast event, several observed event days** (in W, or consecutive days forming one episode): one hit.
  Episodes are never counted per day within a case.
- **One observed event day and several forecast events:** within one issue this cannot happen (one item per risk
  and point). **Across issues**, a reference event day d lies in the horizon of up to six consecutive daily
  issues. Each issue is a separate issued forecast, so each case has its own outcome; this is standard per-issue
  verification, not double counting within a case.
- To keep this visible:
  1. every result is also reported **stratified by issue-relative day** (the first day of W, or of H for
     forecast-no cases, relative to I);
  2. the event floors (§11) count **distinct observed event days (p, d)**, never cases;
  3. intervals use the 7-day block bootstrap on **issue dates**, so the overlap between consecutive issues is
     resampled together.
- **Overlapping events of the same risk across issues:** outcomes are never merged across issues, and issued
  items are never "carried forward".
- **Not used (decision Q1):** peak-date matching, and any silent simplification to same-day matching.

**Flood (rain part):** the same scheme with the reference 72-h accumulation ending on day d, compared with the
issued level **only for items whose wet-soil flag is known to be false** (§7).

## 5. What is verified: the issued output, not a model

- The forecast side of every case is CORE's issued `level` and period, as archived.
- ECMWF, GFS, ICON, the three-model agreement, `core_daily` values and any rule replay **never replace** the issued
  level.
- `core_daily` is used in D3 only as an integrity check: re-applying CORE's rule to the values CORE displayed
  must give the issued level. Where it does not, the case is listed, not corrected.
- Best-match composition (which model Open-Meteo uses over India at each lead) is not documented in the archive.
  It is recorded as not documented in the available evidence, is never inferred from the ECMWF/GFS/ICON
  verification work, and is carried conservatively into provenance (Q6).

## 9. Formal outcome definitions (every verifiable risk)

As in §4, per (p, r, I, ℓ). In addition:
- **No forecast event:** L < ℓ. The case is a miss or a correct negative, judged over the whole horizon H(I).
- **No observed event:** a false alarm or correct negative only if every day that must be checked has a
  reference value.
- **Multiple events:** at most one outcome per case (§4).
- **Overlapping events:** handled per issue, never merged (§4).
- **Missing reference data:** never "no event", never a correct negative, never zero rain, never a success. The
  case is **excluded** with a reason. Forecast-side reasons (item absent: the day was refused and there is no
  release) and reference-side reasons (IMD not published, E; cell outside 30 km / islands, G; ERA5 not yet
  released, E) are kept **separately**, as in VM-1.1 §6.

## 10. Metrics

The same definitions as VM §8 and M4.4-B:
- POD = a/(a+c)
- FAR = b/(a+b)
- CSI = a/(a+b+c)
- frequency bias = (a+b)/(a+c)
- base rate = (a+c)/n

Also:
- A zero denominator gives "no value".
- The four counts are always published with the ratios.
- Intervals: 95 %, 7-day block bootstrap on issue dates, 1,000 resamples, seed per VM-1.1 §21.
- The degenerate-interval label applies (VM-1.1 §21).
- No aggregate across risks, levels or references; no "CORE accuracy score".

## 11. Sample floors (carried forward; never lowered)

| Floor | Value |
| --- | --- |
| Earliest review | ≥ 90 archived prospective days (VM §11). This is a review point, **not** a publication trigger |
| POD at level ℓ | ≥ 20 **distinct observed event days (p, d)** at ≥ ℓ among eligible cases |
| FAR at level ℓ | ≥ 20 issued items at ≥ ℓ. **Every eligible daily CORE-issued item is in the FAR denominator** (decision Q4). Distinct observed event episodes are reported separately as context only; case-level FAR is never replaced by an episode-level FAR |
| CSI, frequency bias | both of the above |
| Pooled result | also n ≥ 300 cases, ≥ 60 issue dates, ≥ 10 points (VM §11) |
| Region / high-altitude / season subgroup | n ≥ 300, ≥ 60 issue dates, ≥ 3 points, plus the event floors within the subgroup |

Below any floor the result is **INSUFFICIENT SAMPLE** and no value is computed. Collection continues.

## 12. The IMD 2026 limitation

- **Until IMD publishes 2026:** only ERA5-based (interim/secondary) rain and flood-rain results are possible.
  They are labelled as such and never presented as gauge verification.
- **When IMD 2026 appears:**
  1. add a new immutable reference supplement (e.g. `history-imd-raw-2026`), with the reference version recorded;
  2. leave every existing release unchanged;
  3. rerun only the affected IMD-based M4.4-D analysis, as a new versioned result;
  4. keep the ERA5 results as they were.
- Before that, nothing is verifiable against IMD, and no IMD-based statement about the prospective period may be
  made.

## 13. GFS source-resolution limitation

GFS rainfall source representation changes at leads 5–7. The effect on verification metrics and on the
agreement distribution is unresolved (VM-1.1 §21).

- In M4.4-D the limitation concerns **provenance**, not the issued level. CORE's level comes from best-match,
  whose composition is unknown (Q6).
- **Flag rule (D3):** a case is flagged `gfs-lead5+` when any day in W (or in H for forecast-no cases) has hours
  more than 120 h after the GFS run time in `model_runs_note`, **and** the GFS model is part of the item's
  agreement basis. The flag is also set when best-match composition is unknown and the window extends beyond
  +120 h of the GFS run.
- Flagged cases are **not corrected, not smoothed and not excluded**. Results are reported with and without them
  as a stratification, labelled as a limitation.

## 14. Model agreement

`agreement_basis` is recorded per case as **contextual provenance** (parsed k and n where the text has that
form). It never enters the outcome or the metric. There is no agreement-adjusted score and no weighting. A future
stratification by CORE's agreement text is exploratory and needs a separate owner decision.

M4.4-C (same-day, same-threshold k of 3 for the raw models) is a different quantity from CORE's ±1-level/±1-day
agreement text and does not validate it.

---

## 15. Geography

The unit is the **point**: the 36 fixed archive points, one representative district point per State/UT.
District, state and region (VM §12) are separate reporting dimensions. No national claim is made; a pooled
result means "over the eligible archive points".

Carried forward:
- **High altitude:** a ≥ 1000 m diagnostic flag; no elevation adjustment.
- **Islands:** a separate region, with no IMD cell within 30 km (G).
- **METAR:** not a reference for any verifiable risk here.

---

## 16. Missing data

Carried forward from VM-1.1 §6:
- Missing is never zero, never "no event", never a correct negative and never a success.
- Each excluded case carries its **forecast-side** and **reference-side** reasons **separately**, with the
  primary-reason precedence D > C > B > A > E/F/G.
- A day refused by the archive (no release) means no CORE item exists for that issue date. That is a
  forecast-side gap, not a negative case.

## 17. Data lifecycle

```
forecast generated (Open-Meteo runs)
      ↓
CORE risk generated (core_generated_at_utc)
      ↓
risk archived (immutable daily release + archive-index record)       ← COLLECTING
      ↓
reference period completes (last day of H(I) ends: I+6, 24:00 IST)
      ↓
reference becomes available (ERA5: several days' lag; IMD: after the annual 2026 file is published)
      ↓
matching performed (D2/D4)
      ↓
eligibility determined (D3: available / excluded with reasons)
      ↓
event outcome assigned (hit / miss / false alarm / correct negative)
      ↓
metric calculated only when the floors are met (D5)                  ← READY FOR REVIEW → VERIFIED
```

A newly issued item is **never** "verified" before its horizon has ended **and** its reference is available.

## 19. Reproducibility record (every future M4.4-D result)

The record contains:
- the prospective release tags with their manifest SHA-256 values;
- the CORE version (`core-v1.0` / `2840f8d`, assumed; the API reports none) and the criterion-text fingerprint
  once archived;
- the verification code commit and the methodology version;
- the reference dataset and version (ERA5 retrieval date and hash, or the IMD 2026 supplement tag);
- the reference hierarchy used;
- the issue-date range and horizon definition;
- the points and geography dimensions;
- the risk type and level;
- the sample filters and floor results;
- the matching rules (tolerance, horizon, day definitions);
- the metric definitions and the bootstrap settings;
- the result table SHA-256.

Inputs are immutable releases and versioned reference supplements only.

## 20. Reporting language

**Use:**
- "CORE issued … (level, period) for point p on date I."
- "The reference subsequently recorded …"
- "In the archived sample (period, points, reference), X of N cases …"

**Do not use:** "CORE predicted the impact", "CORE saved / prevented", "the model knew", "confidence",
"probability", "chance", "likelihood", "guaranteed", or any causal or impact claim.

CORE's own API field is named `confidence`. Reports refer to it only as **"CORE's agreement basis"**.

---

## 21. Entry criteria for M4.4-D scoring (all required; 90 days alone does not trigger scoring)

1. Prospective CORE outputs archived: immutable releases, integrity verified.
2. At least 90 archived days since 28 Sep 2026. The earliest date is **27 Dec 2026**, if no further day is
   refused; each refused day moves it later.
3. The reference is available for the whole horizon of the issues being scored (ERA5 now; IMD after publication).
4. The risk-specific event floors (§11) are met for the result to be published.
5. The matching rules are frozen: Q1 (tolerance), Q2 (IMD day mapping) and Q3 (day I+0).
6. The reference hierarchy is frozen (§6).
7. The methodology version is frozen (a VM version recording §4–§11 as approved).
8. Integrity checks pass (D6).

**Readiness is determined only by the actual prospective sample.**
- 27 Dec 2026 is the earliest review point. Nothing implies that any risk level will reach its event floor by
  that date.
- Against IMD, nothing is possible until IMD publishes 2026.
